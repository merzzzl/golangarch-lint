# GOLANGARCH

Architecture instructions generated from .golangarch.yml. Follow these rules when creating, moving or editing Go code.
Do not edit this file manually; regenerate it with golangarch-lint docs. Verify changes with golangarch-lint lint .

## General instructions

- Keep package names equal to their directory names. Package main and the project root package are exempt.
- Keep every directory containing Go files covered by an architecture rule. Test files are ignored by the linter.
- Apply a matching file rule instead of its directory rule; do not inherit constraints from the replaced rule.
- Treat all path and ignore patterns as relative to the project root. A single star matches within one path segment; a double star spans any depth.
- Apply declaration permissions independently of layout, signatures, imports and calls. Allowing a name does not exempt it from any other check.
- Where both allow and deny lists exist, enforce the deny list first. An omitted allow list is unrestricted; an empty allow list allows nothing except the documented standard-library exemptions.
- Resolve interface calls to possible concrete implementations when checking direct call targets. Do not attribute calls inside a service to its caller: usecase -> service -> repos is allowed when each direct transition is permitted. Builtins are not package calls.
- Treat errors as failures. Report consolidation suggestions and unresolved call targets as warnings; warnings do not fail the command. Call analysis covers the current build environment, may overapproximate targets, and cannot fully resolve reflection or unsafe behavior.
